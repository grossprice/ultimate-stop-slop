# Plans and answers

These rules cover a plan, a proposal, or a reply to the person who asked for the work.

## Drop nothing

Every point the person raised appears in the plan or answer, with what happens to it: done,
planned, out of scope with the reason, or a question asked.

- Before sending, reread the person's message and list each request, constraint and aside.
  Check each one off against the plan.
- An aside ("also, add this to the skill") is a request. It gets its own line.
- A point you decided against still appears, with the reason, so the person can overrule it.

## Leave nothing open

A plan or answer that depends on information you lack does not ship with the gap in it.

- No "open questions" section, no "TBD", no "to confirm", no "we can decide later".
- Ask instead, with a multiple-choice question tool such as AskUserQuestion, as many rounds as
  it takes. Four questions per call is fine, and so are five calls.
- An open-ended question with no sensible options (a name, a wording, a figure only the person
  knows) ends your turn. Ask it and wait for the answer.
- A stated assumption is fine only where both readings produce the same work. Where two
  readings produce different work, ask.
- When two of the person's answers conflict, ask which one wins. Don't pick.
- Found something the person did not know about (a pending change in the working tree, a stale
  note, a contradiction between two docs)? Raise it as a question when it changes the work.

## How to ask

- Ask after reading the material, not before. A question the files already answer wastes the
  person's time.
- Put your recommendation first and mark it "(Recommended)".
- In each option, state the trade-off honestly, including the downside of the one you
  recommend. People pick against the recommendation when they read the cost, and that is the
  point of asking.
- One decision per question. A question whose answer does not change the work is not worth
  asking.

## Show, inline

- A UI change gets a mockup drawn inline in the plan as ASCII inside a code block. Not a link to
  a separate prototype, unless the person asks for a clickable one.
- When choosing between layouts, put each layout's ASCII in the option preview.

## Write the plan in the same voice

Every rule in this skill applies to the plan itself: no em dashes, no filler, active voice,
sentence case, no claims you have not checked.
